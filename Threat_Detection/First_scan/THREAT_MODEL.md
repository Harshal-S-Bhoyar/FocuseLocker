# FocusLocker Threat Model

## 1. Overview
This threat model outlines the attack surface, assets, and trust boundaries for the **FocusLocker** application, encompassing both the Android client (`app/`) and the Node.js API server (`backend/`).

## 2. High-Value Assets
* **Backend:**
  * **OTP Codes:** Used for trusted contact verification and early unlock requests.
  * **Email Quota / Credentials:** SMTP credentials and sending reputation.
* **Android Client:**
  * **Session State & Configurations:** Stored locally (Room DB / DataStore), detailing active blocking sessions, chosen categories, and keywords.
  * **Security Privileges:** Accessibility Service, VPN Service, and Device Admin.

## 3. Entry Points & Attack Surface
### Backend (Node.js/Express)
Exposed to the public Internet, accepting JSON payloads:
* `POST /contact/verify-contact`
* `POST /contact/confirm-contact`
* `POST /unlock/request-unlock`
* `POST /unlock/verify-unlock-otp`

### Android Client (App)
Exposed to the Android OS, other local applications, and the local file system:
* **MainActivity:** Exported (`android:exported="true"`)
* **FocusDeviceAdminReceiver:** Exported (`android:exported="true"`)
* **BootReceiver:** Exported (`android:exported="true"`)
* **AccessibilityService & VpnService:** Process untrusted data (browser URLs, window content, network packets).
* **OverlayService:** Draws over other apps.

## 4. Trust Boundaries
* **Internet <-> Backend API:** Any data entering `req.body` is completely untrusted.
* **Android OS / Apps <-> FocusLocker App:** Intents received from the OS or other apps must be validated. URLs and text content read by the AccessibilityService are untrusted and controlled by the user/websites.
* **FocusLocker App <-> Backend API:** Traffic is assumed trusted in intent but vulnerable to interception if not encrypted (HTTPS).

## 5. Threat Generation (STRIDE)

| Threat Type | Description | Target | Potential Impact |
| :--- | :--- | :--- | :--- |
| **Spoofing** | Attacker spoofs an unlock request by calling the `/request-unlock` endpoint on behalf of a victim. | Backend API | Nuisance emails sent to trusted contacts. |
| **Tampering** | A tech-savvy user modifies the local Room DB to clear active sessions or remove blocked keywords. | Android Client | Complete bypass of the blocking mechanism. |
| **Repudiation** | Lack of comprehensive audit logs for when an "Emergency Bypass" was triggered. | Both | Inability to track circumvention events. |
| **Information Disclosure** | OTPs potentially logged in plaintext or transmitted over HTTP instead of HTTPS. | Backend API | OTP interception leading to unauthorized unlocks. |
| **Denial of Service** | An attacker repeatedly hits `/request-unlock` or `/verify-contact`, exhausting email sending quotas. | Backend API | Service downtime; legitimate users cannot unlock or verify contacts. |
| **Elevation of Privilege** | A malicious app exploits exported components (e.g., `MainActivity` with deep links) to force an unintended state transition. | Android Client | Unauthorized app state manipulation. |
| **Elevation of Privilege** | User forcefully disables Device Admin or Accessibility permissions via adb or safe mode. | Android Client | Total circumvention of the app's core purpose. |
